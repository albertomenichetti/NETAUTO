# ADR 0012: DataType REST API

## Status

Accepted

## Context

NETAUTO needs a stable HTTP boundary for the DataType engine while keeping
transport concerns, orchestration, domain logic, and persistence separated.

## Decision

The REST API is the public interaction boundary, and the CLI consumes REST
only. FastAPI routers remain thin transport adapters while the application
service owns orchestration. A DataType UnitOfWork protocol decouples the
application layer from SQLAlchemy. Pydantic v2 is used only for static API
DTOs; dynamic DataTypes remain domain plus JSON Schema concepts. The request
boundary is strict and performs no implicit coercion.

The API exposes logical DataType identity separately from exact versions. The
DataType resource itself exposes exact version operations and no generic
`/latest` resource. Multiple PUBLISHED versions may coexist. PUT draft
revision is full replacement. Create-next explicitly names `source_version`.
Error responses use a stable NETAUTO envelope. OpenAPI generated by FastAPI is
the canonical API contract.

This does not mean the entire system lacks omitted-version resolution. Other
workflows, such as ObjectTemplate property input and Object creation, may
explicitly resolve the highest `PUBLISHED` version and then persist an exact
pin.

## Consequences

Transport logic stays thin, persistence remains swappable behind the
application layer, and API consumers can rely on a stable contract without
duplicating domain rules.
