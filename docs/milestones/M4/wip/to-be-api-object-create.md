## Public contract

```http
POST /api/v1/core/objects
Content-Type: application/json
```

Query parameters: none.

The Object id is generated by the kernel/server and is never caller-supplied.

### Request

```json
{
  "object_template": {
    "id": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
    "version": 4
  },
  "canonical_name": "server-1",
  "properties": {
    "hostname": "srv01"
  }
}
```

Conceptual wire model:

```text
ObjectCreateBody
    object_template: ObjectTemplateSelector
    canonical_name: string | omitted
    properties: object<string, JsonValue> | omitted

ObjectTemplateSelector
    id: UUID
    version: positive integer | omitted
```

`object_template.version` semantics:

```text
present
    -> request exactly (template_id, version)

omitted
    -> resolve the current default_version of template_id
```

There is no latest/highest-PUBLISHED fallback. If no current default exists, implicit CREATE fails.

Explicit JSON `null` is not omission.

### canonical_name

```text
optional in CREATE
omitted -> generated Object UUID string
required in persisted Object state
mutable
non-unique
not an identity
length 1..255
```

Global uniqueness was evaluated and rejected because legitimate names such as `eth0`, `disk0` and `port1` can repeat across distinct Objects.

Authoritative identity remains `Object.id`.

### properties — sparse canonical JSONB

`properties` is the complete initial runtime value map supplied by the caller. Omitted `properties` is treated as `{}` before semantic validation.

ObjectTemplate `migration_default` is not a CREATE default mechanism.

Frozen absence semantics:

```text
optional SCALAR omitted
    -> key absent

optional LIST omitted
    -> key absent

optional LIST = []
    -> canonicalizes to key absent

JSON null runtime value
    -> invalid

required property omitted
    -> invalid

required LIST = []
    -> invalid
```

Example:

```json
{
  "hostname": "srv01"
}
```

is persisted as exactly:

```json
{
  "hostname": "srv01"
}
```

rather than materializing absent optional keys as `null` or `[]`.

This sparse representation is intentional for the future M5 search workload: ObjectTemplate schema remains the authority for which properties conceptually exist, while `objects.properties` contains only runtime values actually present. Future GIN/operator-class/index choices remain a separate architecture decision.

### Success

```http
201 Created
Location: /api/v1/core/objects/{new_object_id}
```

Response body: none.

The canonical Object representation is obtained through `GET /api/v1/core/objects/{object_id}`.

# TO-BE execution model

CREATE has three deliberately separate stages:

```text
STEP 1 — current binding resolution / early admission
    PostgreSQL

STEP 2 — semantic preparation / validation
    worker-local cache only

STEP 3 — short mutation Unit of Work
    PostgreSQL
```

## STEP 1 — exact binding + current PUBLISHED admission

Every CREATE must establish one exact binding:

```text
(template_id, version)
```

This step always consults PostgreSQL. Cache state must never resolve a mutable current default and must never prove current `PUBLISHED` status.

Explicit selector:

```text
input: (T,V)
DB proves exact (T,V) exists and status == PUBLISHED
output: binding (T,V)
```

Implicit selector:

```text
input: T
DB resolves T.default_version = V
DB proves exact (T,V) exists and status == PUBLISHED
output: binding (T,V)
```

Once resolved, the command remains pinned to that exact binding. A later concurrent `SET_DEFAULT` does not retarget the in-flight CREATE.

### STEP-1 performance requirement

STEP 1 is unavoidable even with a fully warm worker cache, therefore it must be the cheapest practical database path for exactly:

```text
resolve exact binding
verify current PUBLISHED state
```

It must not load effective schema, parent chains, DataType semantics, component declarations or unrelated model metadata.

The exact SQL and physical indexes are intentionally deferred to the subsequent architecture-wide index review. That review must prove efficient explicit-version and implicit-default access paths with no avoidable scans, recursion or reconstruction.

## STEP 2 — validation always consumes READY cache state

After STEP 1, CREATE owns one exact binding, e.g.:

```text
(Server, 4)
```

The Object candidate is validated only from worker-local immutable/stable semantic cache state.

Strong rule:

> CREATE never validates properties by directly traversing ObjectTemplate/DataType persistence. Missing knowledge is first brought into cache; validation starts only from a complete READY cache state.

### Validation-ready facet

Conceptually, the cache facet for `(T,V)` is READY when it contains all stable/immutable knowledge needed by CREATE, including:

```text
stable template admission semantics
    abstract flag / direct-creation eligibility

complete effective property schema
    declaring_template_id
    name
    value_mode
    required
    exact datatype_id/version pin

all referenced exact DataTypeVersion semantics
    stable primitive/base type
    canonical immutable constraints

compiled runtime validation structures
    RuntimePropertySpec or equivalent
    reusable compiled regex/enum/validator artifacts where useful
```

The current `PUBLISHED` lifecycle state is intentionally excluded from this cache and remains PostgreSQL authority in STEP 1 and STEP 3.

Because `abstract` is stable model knowledge rather than mutable lifecycle state, direct-creation rejection for an abstract ObjectTemplate is resolved from this READY semantic cache rather than making STEP 1 load extra model metadata.

### Warm path

```text
lookup validation facet (T,V)
    -> READY

check stable direct-creation eligibility
validate/canonicalize properties entirely in memory
```

No model-plane DB read occurs during validation.

### Missing or partial cache

Examples:

```text
components facet READY
validation facet MISSING
    -> fill validation facet

property schema present but one referenced DTV semantic entry missing
    -> complete missing immutable knowledge
```

Partial state is never used for ad-hoc validation.

The invariant is:

```text
ensure READY
    -> validate
```

### Cold fill

Cold fill is a reusable semantic-cache capability, not the Object mutation UoW.

Target shape:

```text
cache miss/partial for (T,V)
    -> bounded bulk immutable PostgreSQL load
    -> effective property materialization
    -> required exact DTV semantic payloads
    -> opportunistic exact DTV cache fill
    -> compile runtime validators/specs
    -> mark validation facet READY
    -> validate through the same cache path used when warm
```

Cold fill must not regress to recursive parent traversal plus N+1 DataType reads.

STEP 2 outputs a complete candidate:

```text
ObjectCandidate
    id
    canonical_name
    template_id
    template_version
    canonical sparse properties
```

No further ObjectTemplate/DataType semantic reconstruction is needed by CREATE.

## STEP 3 — short mutation UoW

Only after STEP 2 has produced a valid candidate does CREATE enter its true mutation Unit of Work.

The UoW must not contain cache fill, compilation or Object semantic validation.

### Final exact-version admission

STEP 1 is an unlocked preparatory observation. Therefore STEP 3 must re-admit the already selected exact binding as still `PUBLISHED` and protect it against lifecycle mutation through commit.

Required semantic predicate:

```text
new Object -> exact OTV binding
    may commit only while the target exact OTV remains PUBLISHED
    through the binding commit
```

This realizes the existing new-binding-admission (`BA`) concurrency rule.

Superseded preferred statement direction for the Object-only persistence portion:

```sql
WITH admitted AS (
    SELECT 1
    FROM object_template_versions
    WHERE template_id = :template_id
      AND version = :template_version
      AND status = 'PUBLISHED'
    FOR SHARE
)
INSERT INTO objects (
    id,
    canonical_name,
    template_id,
    template_version,
    properties
)
SELECT
    :id,
    :canonical_name,
    :template_id,
    :template_version,
    :properties
FROM admitted
RETURNING id;
```

The current revalidation extends this final business statement to materialize `object_component_slots` from the admitted exact effective-component rows while preserving the same semantic admission rule.

`FOR SHARE`, or an equivalent mechanism with the same conflict behavior, is needed because lifecycle/status updates of the exact OTV must not pass while the new binding is committing.

### Lifecycle event

The same transaction then performs one simple `CREATED` lifecycle insert.

The candidate statement split remains:

```text
BEGIN

S1
    final PUBLISHED admission
    + exact OTV protection
    + INSERT Object
    + candidate INSERT all object_component_slots

S2
    INSERT CREATED lifecycle event

COMMIT
```

Object state, materialized current slot contract and the required creation event must be atomic by transaction semantics. If slot or lifecycle persistence fails, the Object insert rolls back too.

## Concurrency behavior

No model-plane PostgreSQL lock is held during:

```text
cache lookup
cold cache fill
validator compilation
stable abstract/direct-creation check
property validation
canonicalization
```

The final exact-OTV protection starts only once the candidate is ready to write.

Race where DEPRECATE wins first:

```text
CREATE STEP 1 sees (T,V) PUBLISHED
CREATE STEP 2 validates from cache
DEPRECATE(T,V) commits
CREATE STEP 3 final admission sees DEPRECATED
    -> no Object binding commits
```

Race where CREATE final admission wins first:

```text
CREATE STEP 3 protects PUBLISHED (T,V)
CREATE inserts Object + current slot materialization + CREATED event
DEPRECATE(T,V) waits
CREATE commits
DEPRECATE may then continue
```

A concurrent default change after STEP 1 does not retarget the resolved exact binding.

## Cost target — partially reopened

Warm worker statement count may remain:

```text
STEP 1
    1 minimal PostgreSQL binding/PUBLISHED lookup

STEP 2
    cache hit
    CPU-only direct-creation check + validation/canonicalization

STEP 3
    1 final-admission + Object INSERT + slot materialization statement
    1 lifecycle INSERT
    COMMIT
```

Additional row work is approximately:

```text
+ one exact-effective-component range read inside S1
+ S object_component_slots INSERT rows
```

where `S` is the new Object effective slot count.

Cold property-validation behavior remains as previously described; component slot materialization should consume the certified DB materialization directly rather than require a new worker cache dependency solely for CREATE persistence.
