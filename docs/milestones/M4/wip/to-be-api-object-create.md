# M4 TO-BE API — Object CREATE

Status: ROUTE-LOCAL CLOSED / M4 WIP / NON-NORMATIVE GLOBALLY

This file records the agreed caller-facing contract and TO-BE execution path for `POST /api/v1/core/objects` during the M4 top-down sweep. The route is closed locally for this sweep. Physical SQL/index design remains an explicit handoff to the subsequent architecture phase and does not reopen the semantic/data-path decisions recorded here.

## Signature

```http
POST /api/v1/core/objects
Content-Type: application/json
```

Query parameters: none.

The Object id is generated by the server/kernel and is never caller-supplied.

## Request representation

Frozen shape:

```json
{
  "object_template": {
    "id": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa",
    "version": 4
  },
  "canonical_name": "server-1",
  "properties": {
    "hostname": "srv01"
  }
}
```

`object_template.version` is optional:

```json
{
  "object_template": {
    "id": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa"
  },
  "canonical_name": "server-1",
  "properties": {
    "hostname": "srv01"
  }
}
```

Semantics:

```text
version present
    -> select exactly that ObjectTemplateVersion

version omitted
    -> resolve the current default_version of the selected ObjectTemplate lineage
```

There is no latest/highest-PUBLISHED fallback. If `version` is omitted and the selected lineage has no current default, CREATE fails.

Conceptual wire types:

```text
ObjectCreateBody
    object_template: ObjectTemplateSelector
    canonical_name: string | omitted
    properties: object<string, JsonValue> | omitted

ObjectTemplateSelector
    id: UUID
    version: positive integer | omitted
```

Explicit JSON `null` is not equivalent to omission for `object_template.version`, `canonical_name` or `properties`.

## canonical_name semantics

`canonical_name` remains optional in CREATE.

When omitted, the generated Object UUID string is used as the persisted canonical name.

Persisted `canonical_name` remains:

```text
required current state
mutable
non-unique
not an alternative identity
semantic length 1..255
```

The authoritative Object identity remains `Object.id`.

The proposal to make `canonical_name` globally UNIQUE was explicitly evaluated and rejected because legitimate component-like Object names such as `eth0`, `disk0` or `port1` naturally repeat across different parents/resources.

## properties semantics — sparse canonical JSONB

`properties` is the complete initial map of runtime values supplied for the selected exact schema. If omitted, it is treated as `{}` before semantic validation.

Required properties must be supplied by the caller. ObjectTemplate `migration_default` is not a CREATE default mechanism.

Optional properties with no runtime value are represented by absence of the JSON key, not by JSON `null` and not by an empty placeholder.

Example schema:

```text
hostname     required SCALAR
description  optional SCALAR
tags         optional LIST
```

Caller input:

```json
{
  "hostname": "srv01"
}
```

Canonical persisted JSONB:

```json
{
  "hostname": "srv01"
}
```

Not:

```json
{
  "hostname": "srv01",
  "description": null,
  "tags": []
}
```

Frozen canonicalization rules:

```text
optional SCALAR omitted
    -> key absent

optional LIST omitted
    -> key absent

optional LIST supplied as []
    -> canonicalizes to key absent

explicit JSON null for any runtime property
    -> invalid

required property omitted
    -> invalid

required LIST supplied as []
    -> invalid
```

This keeps `objects.properties` as a sparse map of values that are actually present rather than a second materialization of the ObjectTemplate schema.

### M5 search/index rationale

The sparse representation is intentional with the future M5 search API in mind.

The ObjectTemplate exact effective schema remains the authority for which properties exist conceptually. `objects.properties` records which values are actually present on one Object.

Therefore:

```text
key present
    <=> runtime value present

key absent
    <=> no runtime value present
```

Materializing absent optional values as JSON `null` would enlarge every Object JSONB document and, with future GIN indexing, would also create avoidable index/storage/update pressure for data whose only meaning is absence.

The exact M5 GIN operator class and search-index design (`jsonb_ops`, `jsonb_path_ops`, expression/partial indexes, or a combination) remain a later architecture decision. The runtime data semantics are frozen independently as sparse canonical JSONB.

## Success response

Successful creation uses:

```http
201 Created
Location: /api/v1/core/objects/{new_object_id}
```

Response body: none.

The caller may retrieve the created representation through the canonical Object GET route.

# TO-BE execution model

The CREATE path is derived from what the command needs, not from the current implementation shape.

The route has three conceptually separate stages:

```text
STEP 1 — current binding resolution / early admission
    PostgreSQL

STEP 2 — immutable semantic preparation / validation
    worker-local cache only

STEP 3 — short mutation Unit of Work
    PostgreSQL
```

The stages intentionally have different authority and lifetime rules.

## Step 1 — resolve exact binding and verify current PUBLISHED state

Every CREATE must establish one exact ObjectTemplate binding:

```text
(template_id, version)
```

This step always consults PostgreSQL. Cache presence must never resolve the current default and must never prove current `PUBLISHED` status.

### Explicit version

Caller supplies:

```text
object_template.id = T
object_template.version = V
```

Step 1 verifies against PostgreSQL that the exact binding `(T,V)` currently exists and is `PUBLISHED`.

Successful output:

```text
binding = (T,V)
```

### Implicit version

Caller supplies:

```text
object_template.id = T
object_template.version omitted
```

Step 1 resolves PostgreSQL current state:

```text
T.default_version = V
exact (T,V) exists
exact (T,V).status == PUBLISHED
```

Successful output is again only:

```text
binding = (T,V)
```

Once resolved, the command keeps this exact binding. A concurrent later change of `T.default_version` does not retarget the in-flight CREATE to another version.

### Step-1 performance requirement

This is a mandatory hot-path database access even when all semantic caches are warm. Therefore it must be designed as the cheapest practical lookup for the two required outcomes:

```text
resolve exact binding
verify current PUBLISHED state
```

The step must not load effective schema, parent chains, DataType semantics, component declarations or unrelated ObjectTemplate metadata.

Physical SQL shape and index selection are deliberately not frozen here. The subsequent architecture/index review must prove that explicit-version and implicit-default resolution have appropriate access paths and do not perform avoidable scans, recursion or model reconstruction.

## Step 2 — validation is always cache-consumed

After Step 1, CREATE owns a selected exact binding, for example:

```text
(Server, 4)
```

All semantic verification of the Object candidate against that exact ObjectTemplateVersion and its exact DataTypeVersion dependencies is performed through worker-local immutable/stable cache state.

Strong rule:

> Object.CREATE does not validate caller properties by directly traversing ObjectTemplate/DataType persistence. Validation executes only from a cache state that is complete/ready for the selected exact binding.

### Cache-ready requirement

Conceptually the validation facet for `(T,V)` is ready only when it contains all immutable/stable knowledge required to validate and canonicalize an Object candidate, including:

```text
complete effective property schema
    declaring_template_id
    property name
    value_mode
    required
    exact datatype_id/version pin

all exact DataTypeVersion semantic payload required by those properties
    stable primitive/base type
    canonical immutable constraints

compiled/runtime validation structures
    RuntimePropertySpec or equivalent
    compiled regex/enum/other reusable validator state where useful
```

Only a complete/ready validation facet is consumed by CREATE.

### Warm cache

```text
lookup validation facet (T,V)
    -> READY

validate/canonicalize caller properties entirely in memory
```

There are no model-plane DB reads during validation.

### Missing or partial cache

A cache miss and a partially populated cache are handled by bringing the required semantic knowledge to a complete/ready state first.

Examples:

```text
components facet READY
properties/validation facet MISSING
    -> load/fill properties validation knowledge

properties known but one required DTV semantic payload missing
    -> complete/fill missing immutable knowledge
```

CREATE must not combine a partial cache with ad-hoc direct persistence validation. The flow is always:

```text
ensure cache READY
    -> then validate
```

### Cold fill

Cold filling is a reusable semantic-cache capability and should use bulk/materialized immutable reads rather than recursive parent traversal or N+1 DataType reads.

Target direction:

```text
cache miss for (T,V)
    -> authoritative bulk immutable projection from PostgreSQL
    -> fill any reusable exact DTV cache entries already carried by the projection
    -> compile worker-local runtime validators/specs
    -> mark validation facet READY
    -> validate candidate using the same cache-consumption path as warm CREATE
```

The cold-fill operation is not the Object mutation Unit of Work. Failure during fill/compile produces no partial Object data-plane state.

### Canonicalization output

Step 2 produces a complete valid candidate with canonical sparse properties:

```text
ObjectCandidate
    id
    canonical_name
    template_id
    template_version
    properties
```

At this point no further ObjectTemplate/DataType semantic reconstruction is required by CREATE.

## Step 3 — short mutation Unit of Work

Only after Step 2 has produced the valid candidate does CREATE enter its true mutation UoW.

The UoW must be short and must not include cache fill, validator compilation or Object semantic validation.

### Final admission requirement

Step 1 is intentionally an unlocked/preparatory current-state observation. The selected exact ObjectTemplateVersion must therefore be re-admitted as still `PUBLISHED` inside the mutation UoW.

This final admission must protect the exact OTV against concurrent lifecycle mutation until the new Object binding commits.

Semantic requirement:

```text
new Object -> exact OTV binding
    may commit only if the target exact OTV remains PUBLISHED through the binding commit
```

This realizes the existing new-binding-admission (`BA`) concurrency predicate.

### Candidate statement shape

The preferred direction is to combine final exact-version admission and Object insertion in one PostgreSQL statement, conceptually:

```sql
WITH admitted AS (
    SELECT 1
    FROM object_template_versions
    WHERE template_id = :template_id
      AND version = :template_version
      AND status = 'PUBLISHED'
    FOR SHARE
)
INSERT INTO objects (
    id,
    canonical_name,
    template_id,
    template_version,
    properties
)
SELECT
    :id,
    :canonical_name,
    :template_id,
    :template_version,
    :properties
FROM admitted
RETURNING id;
```

The exact production SQL remains subject to implementation verification, but the semantic/data-path decision is frozen:

```text
final PUBLISHED admission
+ protection of the exact OTV through commit
+ Object INSERT
```

should be realized without a separate long-lived pre-validation lock window.

`FOR SHARE` (or an equivalent mechanism with the same protection) is required because the final guard must conflict with lifecycle/status updates of the exact OTV, not merely key changes.

### Lifecycle write

After successful Object insertion, the same UoW inserts the required `CREATED` lifecycle event as a separate simple statement.

Conceptual mutation UoW:

```text
BEGIN

S1
    final PUBLISHED admission
    + exact OTV protection
    + INSERT Object

S2
    INSERT CREATED lifecycle event

COMMIT
```

There is no need to combine Object and lifecycle persistence into one oversized SQL statement: transaction atomicity already guarantees that Object state and its required creation event commit together or roll back together.

If lifecycle persistence fails, the whole transaction rolls back and the Object row does not survive.

## Concurrency behavior

No PostgreSQL model-plane lock is maintained while the command performs:

```text
cache lookup
cold cache fill
validator compilation
Object property validation
canonicalization
```

The final exact-OTV protection begins only once the Object candidate is ready to persist.

Representative race:

```text
CREATE
    Step 1 sees (T,V) PUBLISHED
    Step 2 validates from cache

concurrent DEPRECATE(T,V) commits

CREATE Step 3
    final admission sees DEPRECATED
    -> no Object binding commits
```

Opposite order:

```text
CREATE Step 3
    final admission protects PUBLISHED (T,V)
    INSERT Object
    INSERT CREATED event

DEPRECATE(T,V)
    waits for CREATE transaction

CREATE COMMIT
DEPRECATE may then continue
```

A concurrent `SET_DEFAULT` after Step 1 does not retarget the already-resolved binding. Default state is a selector; exact `PUBLISHED` state is the lifecycle-sensitive binding-admission predicate reconfirmed in Step 3.

## Warm-path cost target

With a validation-ready cache:

```text
Step 1
    one minimal PostgreSQL binding/PUBLISHED lookup

Step 2
    cache hit
    CPU-only validation/canonicalization

Step 3
    one final-admission + Object INSERT statement
    one lifecycle INSERT statement
    commit
```

No inheritance traversal, effective-schema reconstruction, exact DataType reads or validator recompilation belongs on the warm path.

## Cold-path cost target

First use of one exact OTV validation facet on a worker:

```text
Step 1
    one minimal PostgreSQL binding/PUBLISHED lookup

Step 2
    cache miss/partial
    one bounded bulk immutable semantic load target
    local cache fill/compile
    validation/canonicalization from READY cache

Step 3
    identical short mutation UoW to warm path
```

Warm and cold paths intentionally converge before Step 3. Mutation persistence does not know or care whether the semantic cache was already warm or was just filled.

## Data structures touched

Authoritative current/mutation persistence:

```text
object_templates
    only where required to resolve an omitted version/current default in Step 1

object_template_versions
    Step 1 current exact status
    Step 3 final lifecycle-sensitive admission/protection

objects
    Step 3 new current Object row

object_lifecycle_events
    Step 3 CREATED event
```

Immutable semantic materialization/cache dependencies:

```text
object_template_effective_properties
    or equivalent frozen M4 effective-property materialization

datatypes / datatype_versions immutable semantic projection as required by cold fill
worker-local exact DTV cache
worker-local ObjectTemplate validation facet/cache
```

`object_components` is not touched by CREATE. Creating an Object does not create ownership edges or materialize empty component rows.

## Denormalization/schema implications

CREATE relies on the M4 decision to materialize immutable effective ObjectTemplate property semantics so a cold cache fill does not rebuild inheritance recursively.

No new Object-table column is required by this route beyond the already agreed intrinsic shape:

```text
objects
    id
    canonical_name
    template_id
    template_version
    properties JSONB
```

The Object row persists the exact binding selected in Step 1 and finally admitted in Step 3.

## Physical index review handoff

Physical indexing is intentionally not frozen route-locally.

The subsequent architecture phase must review the complete workload and prove appropriate indexes for at least:

```text
Step 1 explicit exact-version binding/status lookup
Step 1 implicit current-default resolution
Step 3 exact-version final PUBLISHED admission
Object INSERT FK/support structures
future M5 JSONB search workload
```

Particular emphasis: Step 1 is mandatory even on every warm CREATE, so its explicit and implicit resolution paths must be as fast as practical and must not perform avoidable scans or load unrelated model-plane data.

The index review may alter physical index definitions but must not alter the frozen authority split:

```text
PostgreSQL
    current binding resolution + current/final PUBLISHED admission

cache
    complete immutable/stable semantic validation knowledge

application
    canonicalization/validation

short mutation UoW
    final admission + Object persistence + lifecycle persistence
```

## Route-local closure

Frozen for this route:

- method/path and absence of query parameters;
- server-generated Object id;
- structured `object_template` selector `{id, version?}`;
- explicit-version vs current-default selection semantics;
- optional `canonical_name` with UUID-string fallback;
- `canonical_name` remains non-unique and non-identifying;
- sparse canonical runtime `properties` JSONB;
- optional absent values are omitted rather than represented as JSON null/placeholders;
- `migration_default` is not used by CREATE;
- `201 Created + Location`, no success body;
- Step 1 always uses PostgreSQL to resolve the exact binding and verify current `PUBLISHED` state;
- Step 1 is a minimal mandatory hot-path lookup and receives a later physical-index review;
- Step 2 validation always consumes complete/ready cache state;
- missing/partial semantic cache is completed before validation;
- cold fill is separate from the mutation UoW and should use bounded bulk immutable loading;
- warm and cold paths converge before mutation;
- no model-plane lock is held during cache fill/validation;
- Step 3 re-admits/protects the selected exact OTV as `PUBLISHED` through commit;
- preferred Step-3 shape combines final admission and Object INSERT;
- CREATED lifecycle persistence is a second simple statement in the same atomic UoW;
- `object_components` is untouched by CREATE;
- physical indexes are intentionally deferred to the subsequent architecture-wide workload review.
